# План улучшений react-native-columnar

Рекомендации по производительности, UX, API и инфраструктуре. Пункты упорядочены по приоритету.

**Рекомендуемый порядок старта:** пп. 1–2 (валидация и UAF), 5 (именованные колонки + `defineSchema`), 13 (честный бенчмарк).

---

## 🔴 Корректность и безопасность

### 1. Несовпадение схем почти не ловится

Сейчас JS никак не проверяет, что схема совпадает с буфером. `RangeError` вылетает только когда буфера не хватает. Если перепутать `Int32`↔`Float32` или `Int8`↔`Uint8`, либо забыть колонку в конце, получатся тихо испорченные данные.

- [ ] **Дешёвая проверка прямо сейчас:** после цикла в `createBufferReader` сравнивать `offset === buffer.byteLength` и `header[1] === schema.length`. Размер буфера в C++ ровно равен `kDataStart + byteSize`, поэтому равенство строгое. Это ловит большинство ошибок, кроме перестановок типов одного размера.
- [ ] **Полное решение:** писать коды типов колонок в заголовок, по 1 байту на колонку. В C++ это делается через маппинг `columnTypeOf<T>()`. Тогда JS сможет выдать точную ошибку вида `column 3: expected Float64, got Int32`. Заодно можно читать буфер вообще без схемы (`createBufferReader(buffer)`).
- [ ] Формат при этом меняется, поэтому стоит добавить в заголовок `version`/`magic` и выпустить это в 0.2.0.

### 2. Use-after-free после `toArrayBuffer()`

При перемещении `std::vector` память не перевыделяется, поэтому `cols.*` (`std::span`) продолжают указывать в буфер, которым теперь владеет JS. Если записать в колонку после `return`, это гонка с JS-потоком, а после GC уже UAF.

- [x] Сделать метод rvalue-only: `toArrayBuffer(rt) &&`, тогда вызов выглядит как `std::move(builder).toArrayBuffer(rt)`. Lvalue-перегрузка оставлена с `[[deprecated]]`;
- [x] держать колонки внутри builder'а (`builder.columns()`) и обнулять их при выдаче. `Schema::createColumns(builder)` оставлен как `[[deprecated]]`-обёртка;
- [x] после `toArrayBuffer()` вызовы `columns()`, `resize()` и повторный `toArrayBuffer()` бросают `std::logic_error`;
- [ ] ограничение: копия колонок (`auto cols = builder.columns()`) остаётся незащищённой, обнулить её builder не может.

### 3. Нет `static_assert` на поддерживаемые типы

`X(int64_t, foo)`, `X(long, foo)` или структура скомпилируются, а в JS для них нет соответствующего `ColumnType`.

- [x] Добавить compile-time whitelist: `kIsColumnType<T>`. `static_assert` срабатывает прямо в объявлении схемы, сообщение называет колонку и тип. Дополнительная проверка стоит в `detail::ColumnCursor::addColumn<T>`. `bool`, `char`, `long`, `int64_t` и cv-квалифицированные типы отклоняются.

### 4. Гигиена хедера

- [x] Макросы переименованы в `RN_COLUMNAR_*`, основной теперь `RN_COLUMNAR_DECLARE_SCHEMA`, а `DECLARE_BINARY_SCHEMA` оставлен как алиас. `#undef` вспомогательных невозможен: они раскрываются в коде пользователя уже после подключения хедера.
- [x] Добавлены `#include <cstddef>`, `<cstdint>`, `<memory>`, `<stdexcept>`, `<type_traits>`, `<vector>`. `alignTo` вынесен в `rn_columnar::detail`, дубли из схемы и builder'а убраны.
- [x] Проверка границ при раскладке колонок (`detail::ColumnCursor`) (сделано вместе с п. 2, бросает `std::logic_error`).
- [x] `#pragma pack(1)` убран, вместо него `static_assert(sizeof(BinaryHeader) == 8)`.

## 🟠 API / DX

### 5. Именованные колонки вместо кортежа

Сейчас `const [id, status, isActive, ...] = columns` держится только на порядке, и это главный источник ошибок.

```ts
const Users = defineSchema({
  id: ColumnType.Int32,
  status: ColumnType.Uint8,
  createdAt: ColumnType.Float64,
});

const { rows, columns } = Users.read(buffer);
columns.id[0]; // Int32Array
```

- [ ] Порядок строковых ключей в объекте JS гарантирован, так что раскладка определена однозначно.
- [ ] `defineSchema` один раз заранее вычисляет конструкторы и выравнивания. Тогда при каждом вызове не будет `schema.map` с замыканием и `switch`, а это ощутимо при частых вызовах с малым числом строк (сценарии стримов и кадров).
- [ ] Текущий `createBufferReader` оставить для обратной совместимости.

### 6. Возвращать `rows`, а не `header: Int32Array`

- [ ] `header[0]` вместо `rows` неочевиден, к тому же в C++ это `uint32`, а в JS читается как `Int32`.

### 7. Упростить C++ API

Сейчас нужны две строки:

```cpp
ColumnarWriterBuilder<UserSchema> builder(rows);
auto cols = UserSchema::createColumns(builder);
```

- [x] Класс переименован в `ColumnarWriter`, старое имя `ColumnarWriterBuilder` оставлено как алиас. Колонки берутся через `writer.columns()` (сделано в п. 2), публичное поле `cols` не вводилось, чтобы сохранить проверку на использование после `toArrayBuffer()`.

### 8. Неизвестное заранее число строк

README называет SQLite главным use case, но `sqlite3_step` не знает количество строк. Сейчас приходится делать два прохода (`COUNT(*)`) или копировать данные.

- [x] Один метод `resize(rows)` вместо `truncate` + `finalize`: сжатие компактирует колонки через `memmove` на месте, расширение копирует их в новый буфер (новые строки заполняются нулями). Рост ×2 во время заполнения, в конце `resize(n)`. Добавлен `rows()`.
- [x] Попутно: выравнивание колонок в C++ теперь по `sizeof(T)`, а не `alignof(T)`, ровно как в JS-ридере. Раскладка не изменилась: на всех Android ABI (arm64, armv7, x86_64, i686) и iOS `alignof == sizeof` для поддерживаемых типов. Изменение лишь убирает зависимость от ABI.

### 9. JS-writer для тестов и моков

- [x] Добавлены `createBufferWriter(schema, rows)` → `{ buffer, columns }` и `getBufferSize(schema, rows)`. Буфер байт-в-байт совпадает с выводом `ColumnarWriter` (проверено сравнением с дампом из C++). `Users.create(rows)` появится вместе с `defineSchema` (п. 5).

## 🟡 Производительность

### 10. Обнуление буфера

`buffer_.resize(n, 0)` всегда делает memset. Если все ячейки гарантированно перезаписываются, это лишний проход. На 100–2000 строк не заметно, на сотнях тысяч уже заметно.

- [ ] Debug-сборки (`-O0`): выделение буфера на `std::vector` проходит поэлементный цикл — ~240 µs на 44 KB (2000 строк), тогда как `std::unique_ptr<uint8_t[]>` — ~0.4 µs (на `-O2` оба ≈0). Это искажает бенчмарк в Debug и замедляет dev-сборки. Решение: хранить буфер в `unique_ptr<uint8_t[]>` + размер и делать `resize` вручную. Регрессией п. 10 это не является: старый `vector::resize(n, 0)` на `-O0` ещё медленнее (~284 µs).
- [x] `ColumnarWriter<S> w(rows, Init::Uninitialized)`. Реализовано через аллокатор с default-init (`rn_columnar::Bytes`), а не `make_unique_for_overwrite`: так `resize()` и `shrink_to_fit` работают без изменений. В этом режиме `resize()` тоже не обнуляет новые строки.

### 11. Переиспользование буфера для стримов

Для сенсоров и frame processors сейчас на каждый кадр происходят `new vector` и новый `ArrayBuffer`, а это давление на GC.

- [x] `ColumnarBufferWriter<S>(rt, arrayBuffer, rows)` пишет в существующий `ArrayBuffer`. Буфер может быть больше нужного (в заголовке фактическое число строк), `capacity(byteLength)` считает, сколько строк влезает. В JS буфер выделяется через `createBufferWriter`.
- [x] Ограничения (только JS-поток, старые байты не очищаются, double-buffering) описаны в README.
- [ ] Учесть при реализации п. 1: проверка размера в ридере должна быть `offset <= byteLength`, а не строгое равенство, иначе переиспользуемые буферы не пройдут.

### 12. Работа вне JS-потока

Тяжёлое заполнение builder'а (запрос к БД, обработка кадра) стоит делать на фоновом потоке. `jsi::ArrayBuffer` при этом создаётся только на JS-потоке. Сейчас это нигде не описано.

- [x] Раздел в README с паттерном `CallInvoker` + `Promise` (сниппет проверен компиляцией против `ReactCommon/CallInvoker.h`). Helper в хедер не добавлен: это потянуло бы зависимость от `React-callinvoker` на обеих платформах.

## 🟢 Бенчмарк и пример

Это влияет на доверие к README.

### 13. Бенчмарк легко критиковать

- [x] Baseline создаёт `PropNameID` один раз на вызов, а не на каждую строку.
- [x] Ключи исправлены на `createdAt`/`updatedAt`; все варианты отдают одинаковые данные, а контрольные суммы сверяются между вариантами.
- [x] Сценарии «одна строка» и «полный проход» × 100/500/1000/2000 строк; варианты: объекты, `JSON.parse`, columnar, columnar с переиспользуемым буфером. Результат в µs на вызов (медиана из 5 прогонов).
- [ ] Перемерить на устройстве и обновить таблицу в README: текущие цифры получены старой методикой.

Цифра «208×» в README привлекает внимание, поэтому лучше, чтобы она выдерживала проверку.

### 14. Пример устарел для RN 0.83

- [ ] Используются `RCTCxxBridge` и `[RCTBridge currentBridge]` (legacy). Показать современный путь: `RCTTurboModuleWithJSIBindings` / C++ TurboModule. Пользователи будут копировать именно пример.
- [ ] `init_module` вызывается дважды: в `setBridge` и в `install`.
- [ ] В логе осталась строка `"react-native-ulid-jsi"` после копипасты.
- [ ] На Android в примере JSI-установки нет вовсе, так что Android-путь (prefab + хедер) в рантайме не проверяется.

## 🔵 Пакет, CI, типы

### 15. Скомпилированные типы требуют TS ≥ 5.7

- [ ] `Int32Array<ArrayBuffer>` в `lib/typescript/index.d.ts` у пользователей на TS < 5.7 падает с ошибкой «Type 'Int32Array' is not generic», а `const`-параметры дженериков требуют TS ≥ 5.0. Убрать дженерик или задокументировать минимальную версию.

### 16. Нет тестов

Jest настроен, но тестов нет, а в CI нет шага `yarn test`.

- [x] On-device тесты на react-native-harness (`example/__tests__`, 7 наборов, 69 тестов): C++ writer → JS reader для всех типов и разного числа строк, `Init::Uninitialized`, `resize` (сжатие/расширение/0 строк/рост ×2), ошибки после `toArrayBuffer`, `ColumnarBufferWriter` и `capacity`, async через `CallInvoker`, JS API (`createBufferWriter`/`getBufferSize`), одинаковость данных во всех вариантах бенчмарка. Совпадение раскладки C++ и JS проверяется в рантайме (`__columnarBufferSize` vs `getBufferSize`).
- [ ] Запуск Harness в CI (нужен macOS runner с симулятором и собранным приложением).
- [ ] Быстрые unit-тесты ридера на jest без устройства и `yarn test` в CI.
- [ ] Android: в примере нет JSI-установки, поэтому Harness сейчас гоняется только на iOS.

### 17. Мелочи

- [ ] В podspec `:tag => "#{s.version}"`, а release-it создаёт тег `v${version}`, теги не совпадают.
- [ ] JS-часть не импортирует `react`, так что peer-зависимость от него лишняя.
- [ ] В README вариант `include_directories(${NODE_MODULES_DIR}/...)` ломается в pnpm и монорепах с hoisting; лучше рекомендовать prefab.
- [ ] В CI шаг `bob build --target codegen` есть, но `codegenConfig` в `package.json` нет. Проверить, что этот шаг вообще что-то делает.

## 💡 Развитие (фичи)

- [ ] **`Int64`/`Uint64`** через `BigInt64Array`: rowid в SQLite и наносекундные таймстемпы. Поддержку `BigInt64Array` в Hermes для минимальной версии RN нужно проверить.
- [ ] **Строки**: dictionary-колонка (коды `Int32` + `jsi::Array` уникальных строк). Для low-cardinality данных (статусы, категории) это почти бесплатно. Второй вариант — offsets + UTF-8 blob.
- [ ] **Nullable**: битмап валидности, как в Apache Arrow. В перспективе можно стать совместимым с Arrow, тогда буфер откроется через `apache-arrow` в JS.
